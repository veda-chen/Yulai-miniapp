## 一 结论与边界

羽来V1采用原生微信小程序、TypeScript统一云函数和CloudBase文档型数据库。云函数按业务模块拆分代码，但作为一个 `api` 函数部署；客户端不直接访问业务集合。该方案减少M1部署和登录接入成本，同时把名额竞争、候补递补、参与权限和比分版本冲突集中放在可信服务端处理。

V1的主闭环是发现球局、查看详情、创建球局、报名、候补、退出、变更确认和到场参与。组队与计分是创建球局时可选的现场功能，默认关闭。球局默认公开，也允许组织者改为仅链接可见。学校资料可填可不填，并允许后续修改或清空。

V1不提供线上订场、订单、支付、AA收款、退款、钱包或平台结算。费用字段只展示线下说明。系统不直接复制第三方产品的等级文案，使用羽来自有的五档水平标签：不清楚、休闲、新手、进阶、对抗。

## 二 设计目标

| 目标 | V1验收口径 |
|---|---|
| 组局可靠 | 同一名额的并发报名不会超卖，重复请求不会重复占位 |
| 操作清楚 | 从首页到完成报名不超过三个主要页面，状态和失败原因可见 |
| 权限可信 | 只有正式参与者可录入比分，候补、退出者和外部用户不可录入 |
| 变更可追踪 | 关键球局变更、报名状态和比分修改保留审计记录 |
| 可运营 | 管理端可维护场馆、处理举报、下架内容和查看基础运营指标 |
| 可恢复 | 每日备份，有明确恢复流程；关键数据写入失败时不产生半完成状态 |
| 可演进 | 后续可增加更多场馆、俱乐部和智能排场，无需重写核心数据模型 |

## 四 总体架构

### 4.1 架构视图

用户通过微信小程序访问球局和现场功能。小程序只保存展示缓存，通过 `wx.cloud.callFunction` 调用统一的 `api` 云函数。云函数从运行上下文取得微信身份，并执行权限、名额和比分规则。CloudBase文档型数据库保存业务数据，云存储保存场馆图片和平面图，云日志记录请求ID和关键故障。

| 层次 | 组件 | 职责 |
|---|---|---|
| 客户端 | 原生微信小程序 TypeScript | 页面、表单、状态展示、订阅授权、弱网重试和本地缓存 |
| 运营端 | 轻量Web管理端 | 场馆维护、举报处理、内容下架、用户限制和指标查看 |
| 接口层 | 单一 `api` 云函数动作路由 | 鉴权、参数校验、幂等、稳定错误码和请求ID |
| 业务层 | TypeScript模块化单体 | 用户、场馆、球局、报名、现场、比分、通知、审核和审计 |
| 数据层 | CloudBase文档型数据库 | 事务、唯一索引、版本字段和查询索引 |
| 文件层 | CloudBase云存储 | 场馆图、平面图、用户提交图片和缩略图 |
| 基础设施 | 微信云开发 | 云函数部署、日志、配额和开发/生产环境隔离 |
| 可观测性 | CloudBase日志和指标 | 定位错误、监控调用和追踪关键业务失败 |

### 4.2 技术选型

| 范围 | 建议 | 原因 |
|---|---|---|
| 小程序 | 原生框架加TypeScript | 微信能力接入直接，包体可控，减少跨端框架兼容层 |
| 后端 | Node.js 20云函数加TypeScript | 与前端共享语言，部署单元少，直接取得微信可信身份 |
| 数据访问 | `wx-server-sdk` | 云函数内以管理端访问数据库，客户端权限统一关闭 |
| 数据库 | CloudBase文档型数据库 | 与小程序和云函数同平台，支持事务、索引和弹性容量 |
| 管理端 | React加TypeScript | 生态成熟，表格和表单组件充足 |
| 文件 | 云对象存储加CDN | 降低应用服务器带宽和图片处理压力 |
| 测试 | Vitest或Jest、Supertest、小程序开发者工具 | 覆盖领域规则、API集成和主流程冒烟 |
| 部署 | CloudBase CLI | 配置可复现，适合当前单函数和小团队维护 |

当前不引入微服务、外部消息队列、搜索集群和Redis。通知任务先使用数据库任务集合和定时触发云函数；当任务延迟或热点负载达到阈值时，再引入专用队列或缓存。

### 6.2 关键状态机

球局状态为草稿、已发布、已取消、已结束和已下架。报名状态为已报名、候补、已退出、已拒绝和已递补。比赛状态为待开始、进行中、已完成和已锁定。

状态变化必须由领域服务执行。客户端传来的status只作为请求意图，不能直接写数据库。取消球局、下架内容、结束后锁定比分等高影响动作要写入审计日志。

### 6.3 并发与一致性

报名动作在云数据库事务中读取球局容量和有效报名数，再写入已报名或候补状态。`activityId + userId` 唯一索引阻止重复占位，请求幂等键保证弱网重试返回同一结果。退出时按 `queueNo` 递补最早候补者，并在同一事务内完成状态变化和通知任务创建。

比分写入使用乐观锁。客户端提交match_id、expected_version和比分；若版本已变化，服务端返回最新比分、修改人和修改时间，由用户确认后再次提交。每次修改新增ScoreRevision，不覆盖历史。球局结束后组织者可锁定，锁定后普通参与者不能继续修改；管理员仍可在有理由并审计的前提下纠正。

## 七 关键业务流程

### 7.1 登录

1. 小程序调用微信登录能力取得短期code。
2. 小程序把code发送到羽来服务端。
3. 服务端调用微信服务端接口换取用户标识和会话信息，AppSecret只保存在服务端密钥管理中。
4. 服务端创建或更新用户，签发短期访问令牌和可刷新会话。
5. 后续请求由服务端根据令牌识别用户，永不接受客户端自报openid作为身份依据。

### 7.2 发布与发现球局

组织者填写时间、场馆、人数上限和截止时间。标题可自动生成，场地、水平、费用说明和联系方式可选。发布时visibility默认PUBLIC，grouping_enabled和scoring_enabled默认false。公开球局进入列表和搜索；仅链接可见球局只能通过有效链接进入，不出现在公共列表。

### 7.3 报名与候补

服务端校验球局状态、时间、截止时间、用户状态和重复报名。名额未满写入已报名；名额已满写入候补。退出后自动递补最早候补者。涉及人数的响应都返回服务端最终状态，客户端不自行推算成功。

### 7.4 关键变更确认

开始时间、场馆、取消和显著影响参与的变更会生成ActivityChange，并给正式参与者创建通知任务。参与者再次进入详情时看到变更摘要，可确认继续参加或退出。普通文案修正不强制确认。

### 7.5 组队与计分

只有活动开启对应开关时展示入口。组队V1支持组织者手动调整和简单随机分组。计分入口对正式参与者开放，候补、退出者和未报名用户不可用。录入人和每次修订可见；版本冲突必须先处理，不能静默覆盖。

## 八 接口约定

### 8.1 调用风格

客户端统一调用 `api` 云函数并传入 `action`、`payload` 和 `requestId`。时间使用带时区ISO 8601，云端按UTC存储。需要幂等的动作还携带 `idempotencyKey`。响应返回稳定的业务码、用户可读信息和 `requestId`，客户端不依赖自然语言判断错误类型。

### 8.2 主要接口

| 动作 | 用途 | 权限 |
|---|---|---|
| `auth.session` | 取得或创建当前羽来用户 | 微信身份 |
| `user.getMe` | 当前用户资料 | 登录 |
| `user.updateMe` | 修改或清空学校、水平等资料 | 登录 |
| `venue.list` / `venue.get` | 场馆列表、详情、场地与平面图 | 公开读取，经云函数过滤 |
| `activity.list` / `activity.get` | 公开球局搜索、分页和详情 | 按可见性 |
| `activity.create` / `activity.update` | 创建或修改球局 | 登录；修改限组织者 |
| `registration.join` | 报名或进入候补 | 登录且幂等 |
| `registration.leave` | 退出并触发递补 | 本人且幂等 |
| `activity.ackChange` | 确认关键变更 | 正式参与者 |
| `grouping.generate` | 生成初始分组 | 组织者且功能开启 |
| `score.revise` | 新增比分修订 | 正式参与者且功能开启 |
| `score.lock` | 锁定比分 | 组织者 |
| `report.create` | 举报用户或内容 | 登录 |

### 8.3 基础安全

云函数进行对象级权限校验，不能只依赖页面隐藏按钮。8 个业务集合均为 `ADMINONLY`，客户端无直接读写权限。创建、报名、比分和举报动作分别限流。富文本和用户输入按白名单清洗，图片上传限制类型、大小和数量。`OPENID_HASH_SECRET` 等密钥只进入云函数环境变量，不写入仓库、小程序包或日志。

## 九 隐私与平台适配

收集字段遵循功能最少原则。学校始终可选且可清空；联系方式默认仅正式参与者可见，服务端对不同身份返回不同字段。分析数据优先使用内部user_id，不把微信标识发送给第三方分析服务。用户可申请注销，业务表按法定和运营需要进行匿名化或删除，审计和安全记录执行单独留存策略。

发布前必须在微信公众平台逐项核对隐私保护指引、涉及的接口或组件、服务类目、订阅消息模板、request合法域名、uploadFile合法域名及业务域名。订阅提醒只能在用户主动选择后使用，拒绝订阅不能阻断报名主流程。

## 十 部署与运维

### 10.1 环境

| 环境 | 用途 | 数据规则 |
|---|---|---|
| Local | 本机开发和单元测试 | 依赖注入假的微信上下文和数据访问层 |
| Development | 开发工具和体验版联调 | 当前环境 `cloud1-d1g8z3590d3768cbb`，不保存正式运营数据 |
| Production | 正式运营 | 独立CloudBase环境、独立密钥、最小权限和受控发布 |

### 10.2 持续交付

每次合并先执行格式检查、类型检查、单元测试、M1配置校验和云函数构建。通过后由CloudBase CLI部署到开发环境并执行云端健康检查。生产发布使用独立配置和同一构建产物，集合与索引变更必须向后兼容，并保留上一版云函数代码用于回滚。

### 10.3 监控与恢复

关键指标包括API成功率、P95延迟、登录失败率、报名冲突率、候补递补失败数、通知积压、比分冲突率和数据库连接数。严重错误同时记录request_id、用户内部ID、对象ID和操作阶段，不记录完整联系方式、微信会话密钥或访问令牌。

当前个人版环境不把控制台回档能力视为可用保障。进入试点前需建立定时导出或升级到支持回档的套餐，并执行一次恢复演练；目标恢复点不超过24小时，目标恢复时间不超过4小时。场馆图片和配置文件启用版本或回收站策略。

## 十一 非功能目标

## 十三 测试策略与发布门槛

### 13.1 自动化重点

不为简单页面样式编写脆弱测试。自动化集中覆盖容易造成数据错误或越权的规则：报名容量、重复请求、候补递补、可见性、联系方式权限、正式参与者权限、比分版本冲突、比分锁定和关键变更审计。

### 13.2 发布门槛

| 门槛 | 通过条件 |
|---|---|
| 业务 | 创建到报名闭环、退出递补、取消和变更确认全部通过 |
| 数据 | 并发报名、幂等和比分冲突测试通过，无已知数据损坏缺陷 |
| 权限 | 非参与者无法看受限联系方式或修改比分，普通用户无法调用管理接口 |
| 平台 | 合法域名、隐私保护指引、订阅模板、服务类目和体验版审核项已复核 |
| 运维 | 告警可触达，备份可恢复，回滚步骤在Staging演练通过 |
| 试点 | 场馆名称、地址、平面图、场地编号和现场联系人已核验 |

## 十四 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 微信平台规则或接口变化 | 登录、通知或提审受阻 | 把平台接入封装成适配层；M5再次核对官方后台和文档 |
| 单人开发投入不足 | 里程碑延期 | 先保障组局主闭环；组队与计分可整体后移，不拆半成功能上线 |
| 报名高峰并发 | 超卖或重复占位 | 云数据库事务、唯一索引、幂等键和并发压测 |
| 参与者共同录分冲突 | 结果被覆盖或争议 | 乐观锁、版本提示、完整修订记录和组织者锁定 |
| 场馆资料不准确 | 现场体验差 | 试点前实地核验，管理端支持快速停用和修正 |
| 隐私收集过度 | 审核和信任风险 | 学校可选可清空；联系方式分级返回；上线前数据清单复核 |
| 通知授权率低 | 用户错过变更 | 详情页保留显著变更状态；通知是增强能力而非唯一通道 |

## 十五 后续技术演进触发条件

只有满足可观测条件才增加基础设施。API单实例CPU持续超过60%或P95超目标时增加实例；数据库查询P95持续超过200毫秒时先优化索引和查询；通知任务积压超过五分钟且每周发生三次时引入专用队列；热点读取明显压垮数据库时再加入Redis；只有团队和业务边界扩大到单体部署阻碍独立发布时才拆服务。
