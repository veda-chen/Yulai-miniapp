# 羽来小程序综合优化计划

评审日期：2026-10-14。范围：当前本地工作区的小程序、云函数、工程脚本及发布记录。

## 1. 总体判断

项目已经具备发现球局、创建、报名候补、现场计分、通知、运营管理等完整链路，也已经实现请求过期保护、草稿、部分缓存、通知重试、账号注销及发布门槛。下一轮优先补齐正确性和验收闭环，再提升核心流程效率。暂不建议继续扩大外观设置、增加支付或重写技术栈。

本次是源码评审及本地自动检查，没有连接生产数据库、操作微信平台或运行当前版本真机。视觉建议属于待验证方案，不能视为已观察到的真机缺陷。仓库存在大量既有未提交改动，计划以这些改动后的状态为基线。

本次验证：

- `pnpm check` 完整通过：格式、Lint、类型检查、17 个测试文件 / 90 项单元测试、UI 行为与 M1–M5 自动检查。
- `node scripts/check-release-gates.mjs` 按预期失败：5 项 PENDING，备份恢复 1 项 BLOCKED。这是发布条件未满足，并非自动测试失败。
- 对搜索分页的分支逻辑做了独立最小复现：30 条匹配数据、每页 20 条、扫描批次 100，返回 20 条后 `nextOffset=null`，仍有 10 条未消费。尚未对云数据库执行集成复现。
- 文档中的旧截图、旧性能结果、旧备份仅作历史资料；不能作为当前版本验收结论。

## 3. 关键代码证据与复现场景

### A1：列表分页提前结束

位置：`cloudfunctions/api/src/modules/activity.ts:335–377`。

带关键词或仅余位条件时批次为 100。结果数组不足 100 条即设置 `exhausted=true`，但内部循环可能在已得到一页结果时提前退出。比如数据库返回 30 条且都匹配，请求 20 条，仅消费前 20 条，就因 30 < 100 返回空游标。修复时须同时检查批次内未消费记录，不能只检查返回数组长度。

稳定分页还应加唯一 ID 排序条件；公开列表的新增、删除、时间流逝和筛选变更需要明确刷新规则。

### A2 / A3：状态交错风险

位置：`cloudfunctions/api/src/modules/participation.ts` 的 `startActivity`、`setAttendance`；`cloudfunctions/api/src/modules/live.ts` 的 `generateGrouping`。

- 开始接口读到 OPEN → 另一请求取消活动 → 开始接口无条件写 IN_PROGRESS，可能使取消状态被覆盖。
- 到场接口读到允许修改 → 结束事务写 COMPLETED → 到场接口 `.set()` 写 ACTIVE，可能破坏完成记录。
- 分组在事务外读取草稿、活动和最新轮次，事务内主要写入计算结果；需验证双端请求及结束交错，不能把“使用了事务”视为完整并发保障。

这些是源码可推导的竞态风险，尚非生产事故结论。测试必须控制交错顺序，并补真实 CloudBase 事务验证。

### B1：历史页的空页与跳动

位置：`cloudfunctions/api/src/modules/activity.ts:518`、`apps/miniprogram/pages/profile/history.ts`、`history.wxml`。

报名原始页可全部为候补、退出或尚未开始的记录，过滤后为空，但后面可能仍有历史记录。界面此时会显示“还没有历史球局”，同时提供“加载更多”。客户端每次合并全量记录再排序，还会改变已展示条目位置并扩大 `setData` 数据量。

验收数据：前 20 条均不符合、后续存在历史；相同开始时间的多条记录；分页期间活动结束；超过 200 条历史。不能出现误导性空状态、重复、遗漏或回到顶部。

### B5：性能数据口径不足

位置：`scripts/check-cloud-performance.mjs`、`apps/miniprogram/app.ts`、`apps/miniprogram/services/cloud-api.ts`。

现有脚本覆盖 `health.get` 和 `activity.list`，记录云函数时长及 CLI 调用墙钟耗时；后者不能替代手机端内容可见时间。服务端已经有脱敏入口日志，应在此基础上补客户端关联和告警，而非重复造一套日志。

采样分别报告：冷 / 热启动、服务端耗时、手机请求耗时、内容展示耗时；注明设备、网络、数据规模、并发与失败数。增加历史、我的统计、详情和认证写入接口。旧 20 次样本不能说明长期 P95 稳定。

## 4. 体验、运营和安全验收

### 体验任务

找 5–8 名目标用户完成“首次找局并报名、创建并分享、满员候补、查看到场地点”四项任务，记录成功率、耗时、误触和求助点。此为方向验证，不把小样本当作统计显著性结论。

建议先设试点目标，采集基线后调整：首次找局报名任务成功率 ≥90%；创建流程无需讲解即可完成；新布局使找局任务中位耗时下降 ≥20%。这些是建议目标，不是当前测量值。

视觉采用默认主题全流程，再以深色、大字、320 / 375 / 430 宽度和长名称做组合覆盖；无需穷举全部外观组合。现有照片风格和四个底部入口可继续使用。

### 核心可靠性矩阵

1. 最后一个名额竞争，报名与缩容、退出递补、注销交错：正式人数不超容量，候补顺序与用户状态一致。
2. 开始 / 结束 / 取消 / 签到交错：状态不可逆向恢复，审计与实际状态一致。
3. 分组生成与发布重复、录分与确认冲突：不覆盖已确认数据，不遗留部分记录。
4. 写入已成功但客户端超时：再次进入可核对结果；只有具备幂等语义的写入才能安全重试。
5. 通知双 worker、发送成功但持久化失败：不重复发送，`VERIFY_REQUIRED` 有人工核查入口或操作流程。
6. 拒绝隐私或订阅授权、清空可选资料、注销后旧页面返回：提示和权限一致，敏感信息不可重新展示。

### 发布与运营

- 发布候选必须映射到 Git 提交、微信上传版本、云函数产物、索引版本和环境；先整理当前未提交改动，再生成清单。
- 场馆资料按现场事实核验，缺失或未核验时明确提示；核实入口、场号、开放时段与联系人流程。
- 备份演练必须实际恢复到隔离环境并校验数量、关联及核心页面可读，不能仅生成恢复计划。数据库、云存储及环境配置分别覆盖，密钥单独安全管理。
- 核验云端真实 ACL、定时触发器、密钥配置和告警；仓库配置存在不等于已部署生效。
- 指定举报、通知异常、备份失败和费用异常负责人；试点期间每日查看异常和漏斗，不急于新增社交及支付功能。

## 5. 建议排期

| 阶段 | 时间窗口 | 交付与退出条件 |
| --- | --- | --- |
| 第 1 阶段：正确性 | 第 1–4 个工作日 | A1、A2 优先完成；启动 A3；针对性失败用例先复现再转绿，原有 `pnpm check` 通过；同步预约真机、场馆和隔离环境 |
| 第 2 阶段：可用性 | 第 5–9 个工作日 | 完成 A3、B1；小范围实施 B2–B4，补基础监控 B5；用户任务验证核心入口与表单 |
| 第 3 阶段：试点验收 | 第 10–15 个工作日 | B6、C5、云端并发和隔离恢复；补齐发布证据；门槛通过后才进入试点发布 |
| 试点之后 | 用量数据驱动 | 按扫描数、失败率、包体和反馈决定 C1–C4；每轮只推进一个可测的性能瓶颈 |

这是单名熟悉项目的开发者配合测试 / 运营的约 2–3 周计划，不是固定上线承诺。平台配置和恢复资源受阻时，完成独立开发项并保留门槛，不提前宣告可发布。

## 6. 最先执行的五件事

1. 修复列表分页提前结束，补真实 handler 的边界测试。
2. 修复开始 / 签到与取消 / 结束交错，验证分组并发。
3. 改历史分页、空状态与增量追加。
4. 在当前代码版本上完成两类真机、认证写入并发和恢复演练。
5. 建立最小监控与任务基线，再调整首页、详情和创建流程。

完成标准：关键链路正确、线上异常能定位、核心任务容易完成、发布和恢复有当前版本证据。本次仅新增此计划，未修改业务实现或部署云端。
