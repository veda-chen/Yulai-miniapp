# 羽来产品需求文档
## 组局主流程和可选现场功能 V0.1

日期：2026年9月8日　｜　状态：需求草案　｜　用途：长期运营

## 1 产品结论

羽来是一款面向广州大学城羽毛球爱好者的微信小程序。V1首先解决“发起一场球局并找到合适的人参加”：用户可以发现球局、创建球局、报名、候补、接收关键变更，并在活动结束后留下参与记录。

组队、排场和计分是球局级可选功能。组织者可分别开启，默认关闭。任何可选功能都不能阻塞创建、报名、取消或结束球局。首个试点场馆是广东工业大学大学城校区体育馆，场馆资料在上线前现场核实。

学校是可选资料。用户可以跳过、补填、修改或清空；未填写学校不影响任何核心功能。水平也允许选择“不清楚”，V1不使用趣运动等级说明原文。

## 2 产品目标和边界

| 项目 | V1定义 |
| --- | --- |
| 核心目标 | 让组织者完成发局和报名管理，让球友完成找局和报名 |
| 主要验证 | 用户能否持续创建和参加球局，球局能否顺利成局 |
| 试点范围 | 广东工业大学大学城校区体育馆，至少2名组织者、3场真实活动 |
| 核心闭环 | 发现或创建 → 报名或候补 → 变更确认 → 线下参加 → 活动归档 |
| 可选闭环 | 开启组队 → 发布安排；开启计分 → 参与者录分 → 结果锁定 |
| 非交易边界 | 不提供在线订场、订单、支付、AA收款、退款、钱包和结算 |

V1不覆盖多运动项目、全国场馆、俱乐部体系、正式淘汰赛、瑞士轮、实时室内定位、自动确认场馆库存和复杂战力算法。场地费用可以作为文字说明，不能形成支付状态或欠款记录。

## 3 用户和权限

| 角色 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 游客 | 浏览公开球局和场馆公开资料 | 报名、创建、查看受限联系方式 |
| 登录用户 | 维护本人资料、创建球局、报名和退出 | 修改其他用户资料或其他组织者的球局 |
| 正式参与者 | 查看本球局成员信息；启用计分时录入本球局比分 | 管理他人报名、修改其他球局、直接锁定争议比分 |
| 候补用户 | 查看候补顺序和本人状态 | 录分、进入组队候选名单 |
| 组织者 | 编辑和取消自己的球局、管理报名、开启可选功能、处理比分争议 | 管理其他组织者的球局或平台场馆资料 |
| 平台管理员 | 维护场馆资料、处理举报和下架内容 | 默认不修改球局比赛结果；介入时必须记录原因 |

服务端必须执行权限校验。页面隐藏按钮不能替代服务端鉴权。组织者也是参赛者时占用一个正式名额，并同时拥有组织者权限和参与者权限。

## 4 信息架构

一级导航采用：首页、球局、场馆、我的。创建球局使用首页和球局页的明显按钮。赛场不占固定一级入口；用户参加的球局开启组队或计分后，在首页当日活动卡片和球局详情显示“进入现场”。

| 页面 | 主要内容 | 主要操作 |
| --- | --- | --- |
| 首页 | 当日球局、附近或近期公开球局、本人进行中事项 | 进入详情、创建球局、进入现场 |
| 球局列表 | 时间、场馆、水平、名额和状态 | 筛选、排序、查看详情 |
| 球局详情 | 时间地点、人数、要求、费用说明、组织者、变更和报名状态 | 报名、退出、分享、确认变更 |
| 创建编辑 | 球局字段、可见范围、报名截止、可选功能开关 | 保存草稿、发布、修改、取消 |
| 报名管理 | 正式名单、候补名单、变更确认状态 | 移出、递补、关闭报名 |
| 场馆 | 场馆资料、联系方式、位置说明、场号和平面图 | 查看、纠错、举报 |
| 现场 | 到场状态、可选组队和计分入口 | 组队、发布安排、录分、处理冲突 |
| 我的 | 本人资料、已创建和已报名球局、参与记录 | 编辑资料、再次查看或发起 |

## 5 核心状态

### 5.1 球局状态

| 状态 | 进入条件 | 允许操作 | 退出条件 |
| --- | --- | --- | --- |
| 草稿 | 创建但未发布 | 编辑、删除草稿、发布 | 发布或删除 |
| 报名中 | 发布成功且未截止 | 报名、退出、编辑、分享、取消 | 到达截止时间或组织者关报名 |
| 报名截止 | 报名关闭且未开始 | 查看名单、组织者补入候补、变更、取消、开始 | 开始或取消 |
| 进行中 | 组织者开始活动 | 管理到场、使用已开启的现场功能、结束 | 结束或取消 |
| 已结束 | 组织者结束或超过自动结束条件 | 查看参与记录和锁定结果 | 终态 |
| 已取消 | 组织者取消 | 查看取消原因和历史通知 | 终态 |

系统不以活动开始时间自动进入“进行中”，避免组织者迟到或场地变化导致状态错误。开始与结束由组织者确认；超过结束时间24小时仍未处理时提醒组织者，自动结束策略在试点后决定。

### 5.2 报名状态

报名状态包括正式、候补、已退出、被移出、已参加和未到场。同一用户在同一球局只能有一条当前有效报名。报名成功以服务端返回为准，重复请求不能重复占位。

截止前有正式成员退出时，系统按候补进入顺序自动递补。截止后不自动递补，组织者与候补者确认后手动补入。被移出时组织者必须选择或填写原因，用户能看到原因并可举报。

## 6 组局核心业务流程

### 6.1 创建和发布

流程：登录 → 点击创建 → 填写必填信息 → 选择可见范围 → 设置报名规则 → 按需开启组队或计分 → 预览 → 发布 → 分享。

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 球局标题 | 否 | 默认由日期、时段和场馆生成，组织者可修改 |
| 开始和结束时间 | 是 | 开始早于结束；开始时间不得早于当前时间 |
| 场馆 | 是 | V1优先从场馆库选择；找不到时允许提交新增建议，不直接发布未经核实的场馆页 |
| 场号或位置说明 | 否 | 场地未定时显示“待确认”，不能假装场地已落实 |
| 人数上限 | 是 | 4至40人，默认12人；后续依据真实运营数据调整 |
| 水平范围 | 否 | 可选择“不限”或羽来自有等级；等级说明定稿前使用文字描述 |
| 报名截止时间 | 是 | 默认开始前2小时，可修改但不得晚于开始时间 |
| 费用说明 | 否 | 纯文本，例如“场地费和球费线下AA”；不出现支付按钮或已付款状态 |
| 联系方式 | 否 | 组织者选择不展示、仅正式参与者可见或公开；默认仅正式参与者可见 |
| 详细说明 | 否 | 场馆规则、装备要求、迟到处理等，限制长度并进行内容审核 |
| 可见范围 | 是 | 建议支持公开和仅链接可见；默认公开，试点验证后调整 |
| 组队功能 | 否 | 默认关闭，可在活动开始前开启或关闭 |
| 计分功能 | 否 | 默认关闭，可独立于组队开启 |

发布校验失败时保留用户已填写内容并定位到错误字段。发布成功后生成唯一球局ID和分享入口。重复点击发布只创建一个球局。

### 6.2 发现和查看

球局列表默认展示尚可报名、距离开始时间较近的公开球局。用户可以按日期、场馆、是否有名额和水平范围筛选。首个试点阶段不承诺实时距离排序；位置权限未授权时不影响列表使用。

列表卡片至少显示开始时间、场馆、已报名人数与上限、报名状态、水平要求和组织者昵称。详情页优先显示用户作决定所需的信息，关键字段不能只藏在描述中。

已满活动显示候补入口；已截止、进行中、已结束和已取消活动显示明确状态，不能继续报名。仅链接可见球局不进入公开列表，但持有效链接的用户可以查看并报名。

### 6.3 报名和候补

流程：打开详情 → 检查登录状态 → 查看关键要求 → 点击报名 → 服务端检查状态与名额 → 正式报名或进入候补 → 页面显示最终状态。

报名采用自动通过。若同时多人争抢最后一个名额，服务端保证只有一人进入正式名单，其余按成功顺序进入候补。用户重复点击或网络重试不改变其原有顺序。

用户退出正式名单前看到递补影响提示。截止前退出触发自动递补；截止后退出通知组织者但不自动补人。候补用户退出后，后续候补顺序前移。

### 6.4 编辑和关键变更

标题和描述修改立即生效并记录更新时间。开始时间、结束时间、场馆、场号、人数上限和取消活动属于关键变更。

关键变更后，详情页显示变更前后内容和时间。正式参与者的确认状态重置为待确认；组织者可以看到已确认、待确认和退出人数。关键变更不能把人数上限降到当前正式人数以下，除非组织者先处理超出人员并记录原因。

### 6.5 取消和结束

组织者取消球局时必须填写原因。取消后关闭报名、候补递补和未开始的现场安排，并向现有正式成员和候补成员展示取消状态。已锁定比分保留审计记录，但取消球局不计入长期胜负统计，具体统计口径在试点后复核。

未开启组队和计分时，组织者可以直接结束活动。结束时确认实际参加者，系统生成参与记录。参与记录只表达参加事实，不自动推导水平变化。

## 7 可选组队功能

组织者开启组队后，现场页显示到场确认、组队建议、人工调整和发布安排。未开启时不显示相关入口，数据层也不要求创建轮次或比赛记录。

V1建议采用整轮制。硬约束为每场双打4人、每人同轮最多一场、每片场地同轮最多一场。软目标依次考虑等待时间、上场次数、连续休息、两队水平差、重复搭档和重复对手。系统生成的是建议，组织者确认后才发布。

迟到者从下一轮进入候选；离场者从未发布方案移除；场地停用只调整未开始安排。组织者关闭组队功能时保留已经发布和完成的历史安排，不再生成新轮次。

## 8 可选计分功能

计分可以单独开启。没有使用系统组队时，正式参与者可以手动创建一场对局并从本球局正式参与者中选择参赛人；不能选择候补、退出或外部用户。

本球局所有正式参与者都可以录入本球局比分。每次提交记录操作者、时间和数据版本。多人同时提交不同结果时，系统保留当前结果并提示冲突，不静默覆盖。

比分提交后处于待确认状态。V1建议由对局双方各一名参与者确认相同比分后自动锁定；组织者可以处理冲突并锁定。锁定后才进入比赛战绩。组织者解锁时必须填写原因，系统保存旧值、新值、操作者和时间。

默认规则建议为单局21分、领先2分获胜、30分封顶。该规则是产品默认值，不宣称自动代表最新正式竞赛规则。组织者若不开启计分，系统不生成胜负、胜率或战力数据。

## 9 场馆和场地资料

首个试点场馆为广东工业大学大学城校区体育馆。上线前现场核实场馆官方名称、地址、入口、交通说明、联系电话、开放说明、设施、场号和可用平面图，并记录核实日期与资料来源。

场馆资料缺失时显示“暂无资料”，不得补写推测内容。用户可以提交纠错；管理员审核后发布。个人联系方式和场馆公开电话分开存储并使用不同可见性规则。

2D平面图属于Should功能。图形中的每片场地映射唯一Court ID；无图时仍以场号和位置文字完成组局。平面图高亮表示球局使用的场地，不表示用户实时位置或场馆库存。

## 10 资料和等级

| 用户字段 | 必填 | 规则 |
| --- | --- | --- |
| 微信身份标识 | 是 | 仅用于账号关联，不在用户界面公开 |
| 昵称 | 是 | 可修改，需内容审核 |
| 头像 | 否 | 未设置时使用默认头像 |
| 学校 | 否 | 可跳过、修改和清空；不影响任何核心功能 |
| 自评水平 | 否 | 可选择“不清楚”；与专业资历和认证分开 |
| 个人简介 | 否 | 限制长度并进行内容审核 |

趣运动等级说明原文仅作研究参考，不进入羽来产品。羽来自有等级需要重新确定能力维度、用户可观察的描述和校准方式，避免使用穿着、球拍价格等与实际能力关联弱的条件。

## 11 通知和消息

站内状态是业务事实来源，订阅消息只是提醒。即使微信消息未送达，详情页也必须展示最新报名、候补和变更状态。

建议提醒事件包括报名成功、候补递补、关键变更、报名截止、活动取消和开始前提醒。用户主动订阅后才发送相应微信通知。通知文案不展示不必要的个人信息。

## 12 异常和风控

| 异常 | 系统处理 |
| --- | --- |
| 重复报名或发布 | 使用幂等标识，只产生一个有效结果 |
| 最后名额并发 | 服务端原子占位，其余用户进入候补 |
| 组织者失联 | 详情页提供举报；管理员按运营规则标记或下架，不擅自代为组织 |
| 恶意移出成员 | 记录原因和操作历史，为用户提供举报入口 |
| 多人比分冲突 | 显示当前版本和冲突提示，由参与者重新确认或组织者处理 |
| 弱网 | 明确显示提交中、失败或已保存；失败操作可安全重试 |
| 场馆资料错误 | 展示核实日期，支持纠错并保留审核记录 |
| 敏感或违规内容 | 发布前和发布后审核，支持举报、下架和账号处置记录 |

## 13 非功能要求

普通查询和提交接口的试点目标为p95不超过2秒；24人和6片场地的组队建议目标为3秒内返回。指标须记录设备、网络、部署规格和样本量。

服务端执行身份鉴别、对象级权限校验、输入校验和操作审计。敏感联系方式按可见范围返回，不能依赖前端遮挡。数据传输使用HTTPS，密钥不进入客户端代码库。

上线前完成隐私告知、资料删除申请、数据保留规则、备份恢复演练和跨账号越权测试。具体保留期限、管理员权限审批和处置时限在运营规则中确认。

## 14 数据指标

| 指标 | 定义 |
| --- | --- |
| 发布成功率 | 成功发布的创建尝试数 / 有效创建尝试数 |
| 报名转化率 | 完成报名的详情页独立访客数 / 点击报名入口的独立用户数 |
| 成局率 | 进入进行中或已结束且达到组织者最低人数的球局数 / 已发布球局数 |
| 取消率 | 已取消球局数 / 已发布球局数 |
| 组织者30日复发局率 | 首次发局后30日内再次成功发布的组织者数 / 可观察满30日的首次组织者数 |
| 参与者30日复报名率 | 首次参加后30日内再次报名的用户数 / 可观察满30日的首次参与者数 |
| 可选功能启用率 | 开启组队或计分的球局数 / 进入进行中的球局数 |
| 举报处理时长 | 从有效举报创建到首次明确处置的时间 |

首轮样本小，只报告人数、分子分母和原始比例，不使用少量数据证明长期留存。事件采集需有版本号，指标口径变更后不能直接与旧数据混算。

## 15 验收场景

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| U01 | 学校留空后注册、报名和创建球局 | 全部成功，无补填阻断 |
| U02 | 同一用户连续点击发布或报名 | 只创建一个球局或一条有效报名 |
| U03 | 两人争抢最后一个名额 | 一人正式、一人候补，人数不超上限 |
| U04 | 正式成员在截止前退出 | 第一候补自动递补，双方页面状态一致 |
| U05 | 截止后正式成员退出 | 不自动递补，组织者可手动补入候补 |
| U06 | 组织者变更时间和场馆 | 展示变更前后内容，正式成员变为待确认 |
| U07 | 关闭组队和计分完成一场球局 | 能正常报名、结束和归档，不生成比赛战绩 |
| U08 | 只开启计分 | 参与者可手动建对局和录分，无须系统组队 |
| U09 | 候补用户尝试录分 | 服务端拒绝，不创建比分记录 |
| U10 | 两名参与者同时提交不同比分 | 不静默覆盖，显示冲突并保留操作者记录 |
| U11 | 活动取消 | 报名和未开始现场安排关闭，所有成员看到取消原因 |
| U12 | 场馆平面图缺失 | 用户仍可通过场号和文字位置完成找场 |

## 16 试点计划

在广东工业大学大学城校区体育馆完成至少3场真实球局。第一场验证创建、分享、报名和结束；第二场加入候补与关键变更；第三场按实际需求开启组队或计分。每场8至16人，合计至少20名不同球友。

主流程成功标准：至少80%的受测用户在无指导下完成找局、报名和查看变更；3场活动都能在关闭组队与计分时完成归档；至少2名组织者在试点后再次创建球局。可选功能记录组队耗时、人工调整次数、录分完成率和比分冲突，不阻断主流程验收。

## 附录 核心数据对象

组局核心对象包括User、Venue、Activity、Registration、ActivityChange和OperationLog。可选场馆对象包括Floor、Court和ActivityCourt；可选现场对象包括Round、Match、MatchPlayer、ScoreSubmission和LockedScore。

Activity至少保存组织者、时间、场馆、容量、报名截止、状态、可见范围、联系方式可见范围、组队开关和计分开关。Registration保存用户、当前报名状态、进入顺序、状态变化时间和来源。所有影响名额、关键变更和比分锁定的操作进入审计记录。
